Take an AI app from demo to governed production.

Keel is an open-source Python platform. You describe the whole application in one versioned spec. Every request passes one policy and trace path, and no change ships until its quality, attack and load tests pass.

Quickstart See a request flow GitHub
The problem

Most AI apps are built for the demo.

A team connects a model to a prompt, adds retrieval or a few tools, and ships. Security, scaling, reliability and structure come later. The cost shows up after launch.

↘Silent regressions

A prompt tweak or model swap makes answers worse and nobody notices.

Keel: eval suites gate every promotion.

!Security added later

Prompt injection, data leaks, agents acting beyond their permissions.

Keel: strict profile, guardrails and attack suites on by default.

$Cost and outages

No fallbacks, caching or budgets. Errors under load, bills outrun the plan.

Keel: fallbacks, cache, rate limits and budgets declared in the spec.

?No audit trail

Failures cannot be explained or reproduced. Config is spread across code and dashboards.

Keel: one spec, every step traced, hash-chained audit log.
How it works

Three mechanisms carry five properties.

Secure, scalable, reliable, simple and clean architecture are not separate features. Each comes from three shared mechanisms, and each mechanism serves several properties at once.

1

One spec

A single keel.yaml declares all eight layers, access rules, budgets and eval suites. It is typed, validated, diffed in pull requests and hashed. What is not declared cannot run.

Provenance policy

    
Untrusted content cannot trigger actions.

    
Every piece of data carries labels for its source and trust. Once anything untrusted is in the context, such as a document with planted instructions or any tool output, no tool runs without a human approval. The idea comes from CaMeL and FIDES; Keel implements a simple label-and-gate version.

Eight layers

    
Each layer is a port with swappable adapters.

    
The core depends only on small protocols in keel_core.ports. Local mode ships an in-process adapter for every layer, so the whole stack runs on one machine with no database, Redis or API keys. Production adapters plug in behind the same ports.

    

  






  

    
Plugging in

    
What you need to plug in a backend.

    
An adapter is any class that matches a port protocol. You don't subclass anything. The runtime still makes every access decision, filters what adapters return and traces each step, so a buggy or hostile adapter can't widen what a user may reach.

    

      

        
      

      

        
Declare it in the spec
The spec decides what exists. A tool, source or model that is not in keel.yaml is never offered, and roles must grant it.

        
Implement the port
Match the protocol in keel_core.ports: an async method or two, typed with Keel's frozen dataclasses.

        
Wire it in a composition root
Build an Adapters bundle and a Runtime. keel_local.build_runtime is the reference composition root to copy.

        
Prove it in the gate
Run the contract tests and keel eval. If the new backend changes answers, the quality suite shows it before anything ships.

      

    


    

      
      
      
      
      
    

    

      

      

    


    

      
Rules every adapter must follow

      
    
        
  • Models raise ModelError (or TimeoutError) for failures worth falling back from. Any other exception is treated as an adapter bug: no retry, fall back, trace it.
    • 
        
  • Retrievers return only documents from the sources they are given and set Document.source to the spec source name. The runtime drops anything else.
    • 
        
  • Prompt registries return a version id that changes whenever the template text changes.
    • 
        
  • Caches scope every entry to the principal. Never share entries across users.
    • 
        
  • Tracers never receive prompt text unless observability.log_prompts is true, which the strict profile forbids.
    • 
        
  • Audit logs are append-only and chained, so verify() detects changed, removed or reordered entries.
    • 
      

      
Today vs later. Adapters are wired in code through a composition root. Discovery through Python entry points, so pip install keel-qdrant plus a spec change is enough, is planned but not built yet.

    

  






  

    
Quickstart

    
From zero to a gated app in a few commands.

    
You need uv and Python 3.12 or newer. --offline swaps every model for a built-in extractive model, so no API key is needed.

    


# get the code
git clone https://github.com/achkum/keel-ai-platform.git
cd keel-ai-platform && uv sync

# a new app with secure defaults
uv run keel init my-app

# ask it something, with tracing
uv run keel dev my-app/keel.yaml --offline \
  --ask "When is support available?" --role reader

# run the gate, then pin a release
uv run keel eval my-app/keel.yaml --offline
uv run keel promote my-app/keel.yaml --offline

# which OWASP LLM risks does the spec cover?
uv run keel audit my-app/keel.yaml

      

        
Six commands

        

          
initCreate a starter app on the strict profile.

          
devAsk one question, or serve a local HTTP API on 127.0.0.1.

          
evalRun the quality and attack suites (and load with --load).

          
promoteRun the full gate and pin the version. --list, --rollback.

          
diffShow which settings changed between two spec versions.

          
auditOWASP LLM Top 10 scorecard for the spec.

        

        
Reference apps in examples/: knowledge assistant, support agent with an approval-gated refund tool, and an HR assistant.
